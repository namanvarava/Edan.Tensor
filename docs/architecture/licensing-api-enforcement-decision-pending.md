# 제품 API 라이선스 적용 결정 대기

이 문서는 승인된 개발 라이선스 발급·검증 계약을 제품 API에 연결하기 전에 결정해야 하는 항목을 기록합니다. 이 문서의 선택지는 제안이며, 사용자 승인 전에는 구현 계약이나 공개 API 계약으로 사용하지 않습니다.

## 현재 확인된 사실

- `EDAN.Tensor.LicenseAuthority.sln`은 개발 라이선스 발급·공개키·검증·폐기 HTTP 경계를 제공합니다.
- `EDAN.Tensor.sln`은 LicenseAuthority의 서비스·HTTP 검증 회귀 테스트를 포함합니다.
- 제품 `ApiHost`에는 현재 라이선스 자동 적용 미들웨어나 Endpoint Filter가 없습니다.
- 제품 API의 기존 Tenant·Bearer·Worker·Idempotency 계약은 변경하지 않아야 합니다.
- Development Bypass는 인증 경계일 뿐이며 라이선스 검증을 대신하거나 우회해서는 안 됩니다.

## 승인해야 하는 결정

### 1. 라이선스 토큰 전달 방식

제품 API가 요청마다 라이선스를 전달받는 위치를 정해야 합니다.

| 선택지 | 장점 | 주의사항 |
| --- | --- | --- |
| 전용 `X-EDAN-License` 헤더 | 기존 Bearer 인증과 분리되고 Swagger에서 설명하기 쉽습니다. | 클라이언트와 프록시가 새 헤더를 보존해야 합니다. |
| `Authorization`의 별도 Scheme | 표준 인증 파이프라인과 결합할 수 있습니다. | 사용자 Bearer 인증과 라이선스 토큰을 함께 표현하는 계약이 복잡해집니다. |
| 서버 설정·파일에서만 읽기 | 클라이언트가 토큰을 전달하지 않아도 됩니다. | Tenant별 라이선스와 요청별 기능 검증을 분리하기 어렵습니다. |

권고안은 사용자 인증의 `Authorization: Bearer`와 분리된 전용 헤더를 사용하는 것입니다. 헤더 이름과 다중 라이선스 지원 여부는 승인 전까지 확정하지 않습니다.

### 2. 공개키와 폐기 상태 공급 방식

ES256 공개키만 제품 API에 배포한다는 승인 계약을 만족하면서 KeyId와 폐기 상태를 어떻게 갱신할지 정해야 합니다.

| 선택지 | 장점 | 주의사항 |
| --- | --- | --- |
| 배포 시 JWK 파일 또는 환경 설정 주입 | 외부 호출이 없어 예측 가능하고 운영 장애 면적이 작습니다. | 키 회전과 폐기 목록을 재배포해야 합니다. |
| LicenseAuthority의 JWKS·검증 API 조회 | 키 회전·폐기 상태를 중앙에서 갱신할 수 있습니다. | Authority 장애·네트워크 timeout·캐시 만료 정책이 필요합니다. |
| 서명된 공개키·폐기 목록 번들 배포 | 실행 중 외부 의존성이 없습니다. | 번들 서명·만료·배포 순서 계약이 필요합니다. |

공개키 공급 방식, KeyId별 동시 보관 기간, 폐기 목록 갱신 주기와 Authority 장애 시 허용할 캐시 범위를 승인해야 합니다.

### 3. 기능별 적용 범위

라이선스 기능과 API 경로의 매핑을 정해야 합니다.

| 기능 | 후보 API 범위 |
| --- | --- |
| `Platform` | Tenant·Organization·Project·권한·감사 API |
| `DataSet` | DataSet 메타데이터·콘텐츠·Schema·Validation API |
| `Worker` | 작업·DLQ·Replay·External Delivery API |

기능 매핑이 없는 health·OpenAPI·Swagger 경로의 공개 여부와, 한 요청이 여러 기능을 요구하는 경우의 판정 규칙도 정해야 합니다.

### 4. 오류·상태·관측 계약

다음 HTTP 상태와 안정적인 오류 코드를 승인해야 합니다.

- 라이선스 헤더 누락: `401` 또는 `403`
- 형식·서명·KeyId·기간 오류: `403`
- Tenant·제품·기능 불일치: `403`
- Authority timeout 또는 폐기 상태를 확인할 수 없는 경우: fail-closed 여부
- 응답 본문에 LicenseId·KeyId·상태를 포함할지 여부
- 로그에 토큰·개인키·전체 JWS를 남기지 않는 감사 필드와 추적 식별자

### 5. 개발·운영 환경 경계

다음 동작을 승인해야 합니다.

- Development Bypass가 인증은 제공해도 라이선스 검증을 생략하지 않는지 여부
- 개발 라이선스가 Development에서만 허용되고 Production에서 항상 거부되는지 여부
- 라이선스 설정 누락 시 시작 실패인지, 모든 보호 API를 닫는지 여부
- CI에서 개발 라이선스를 자동 발급하지 않고 임시 테스트 키만 사용하는지 여부

## 재개 조건

위 결정이 승인되면 다음 순서로 구현합니다.

1. 공개 Contracts에 토큰 전달·기능 매핑·오류 코드를 추가합니다.
2. 공개키 전용 검증기와 KeyId·폐기 상태 공급자를 구현합니다.
3. 기존 Tenant·Bearer 인증 이후에 기능별 라이선스 검증 경계를 연결합니다.
4. 정상·누락·위조·만료·시작 전·Tenant 불일치·기능 불일치·폐기·KeyId 회전·Authority 장애 회귀 테스트를 추가합니다.
5. OpenAPI·typed Client·Development/Production 설정·Smoke·Release CI를 갱신합니다.

결정 승인 전에는 제품 API에 임의의 헤더, 상태 코드, Authority 호출, 라이선스 우회 설정을 추가하지 않습니다.
