# EDAN 전역 업무 용어 사전 확장 기준

- 문서 상태: 확장 설계안
- 기준 명명 규칙: [database-naming-conventions.md](database-naming-conventions.md)
- 적용 대상: EDAN 제품군 전체와 SQLite·Oracle·SQL Server·PostgreSQL
- 언어 원칙: 설명·주석·업무 정의는 한국어, 물리 객체명은 영문 소문자
- 주의: 이 문서는 업무 용어 범위와 관계를 확장하기 위한 검토 기준이다. 이 문서의 후보 약어를 전역 충돌 검사 전에 물리 컬럼명에 사용하지 않는다.

## 1. 목적

EDAN은 데이터 플랫폼뿐 아니라 ERP, MES, MOM, QMS, PLM, 설비관리, 설비정보수집, 설비 태그 관리 등으로 확장할 수 있는 공통 명명 체계를 사용한다. 동일한 업무 개념은 모듈과 DB가 달라도 동일한 대표 용어와 대표 약어를 사용한다.

## 2. 사전 데이터 모델

| 필드 | 설명 |
| --- | --- |
| concept_id | 대표 개념의 불변 식별자 |
| module_code | 공통 또는 업무 모듈 분류 |
| concept_group | 엔터티·행위·상태·수량·시간·품질 등 개념 분류 |
| canonical_en | 대표 영문명 |
| canonical_ko | 대표 한글명 |
| canonical_abbr | 전역 유일 대표 약어 |
| related_term | 관계 용어 |
| relation_type | 동의어·유사어·상위어·하위어·혼동 주의어 |
| definition | 포함 의미와 업무 경계 |
| excluded_meaning | 혼동 금지 의미 |
| usage_example | 대표 약어 조합 예시 |
| lifecycle_status | 표준·검토·레거시 호환·폐기 |
| standard_version | 적용 표준 버전 |

관계 용어 테이블은 대표 개념과 1:N으로 연결한다. 관계 용어는 검색과 사용자 입력 동의어 인식에 사용하며 물리 컬럼명 생성에 직접 사용하지 않는다.

## 3. 관계 유형

| 관계 유형 | 설명 | 약어 발급 |
| --- | --- | --- |
| 동의어 | 동일 개념의 다른 표현 | 대표 용어 약어만 사용 |
| 표기 변형 | 단복수, 띄어쓰기, 영미식 표기 | 대표 용어 약어만 사용 |
| 업계 표현 | 특정 산업에서 쓰는 동등 표현 | 대표 용어 약어만 사용 |
| 상위어 | 여러 하위 개념을 포괄 | 별도 개념이면 별도 약어 |
| 하위어 | 상위 개념의 구체 유형 | 별도 개념이면 별도 약어 |
| 문맥 유사어 | 일부 문맥에서만 비슷한 의미 | 자동 통합 금지 |
| 혼동 주의어 | 이름이 비슷하지만 다른 개념 | 절대 통합 금지 |

## 4. 약어 정책

1. 신규 대표 약어는 3자 영문 소문자를 기본으로 한다.
2. 3자 충돌 시 4자로 확장한다.
3. 4자 충돌 시 확정을 보류하고 사람의 검토를 받는다.
4. 같은 약어는 서로 다른 대표 개념에 배정하지 않는다.
5. 업무 모듈별 약어 공간을 분리하지 않는다.
6. 동의어·관계 용어에는 별도 약어를 부여하지 않는다.
7. 기존 2자 약어는 신규 표준에서 사용하지 않는다. 기존 DB/API와 외부 표준 호환을 위해 유지해야 하면 레거시 호환으로 분류한다.
8. 3자·4자 약어는 대표 용어 레코드에만 보관한다. 물리 이름 생성기는 승인된 대표 용어 ID로부터만 약어를 가져온다.
9. 표준 약어 변경은 기존 컬럼 영향 분석, 대체 매핑, Migration 계획 없이 수행하지 않는다.

## 8. 표준화 작업 순서

1. 기존 136개 용어의 대표 개념 여부와 관계 용어를 재판정한다.
2. 중복 개념은 대표 용어 하나로 통합하고 기존 약어는 레거시 매핑으로 보존한다.
3. 3자 약어 전역 중복을 검사하고 충돌 시 4자를 배정한다.
4. 4자 충돌 및 의미 모호성은 검토 보류한다.
5. 287개 컬럼 인벤토리의 현재 이름·제안 이름을 대표 개념 사전으로 재매핑한다.
6. Commercial SQLite DDL의 업무 개념을 별도 대조한다.
7. ERP·MES·MOM·QMS·PLM·EAM·IIoT·TAG 확장 용어를 관계 용어까지 교차 검토한다.
8. 실제 SQLite DB가 제공되면 sqlite_master, table_info, foreign_key_list, index_list를 수집하여 DDL·EF 모델·컬럼 인벤토리와 대조한다.
9. 표준·레거시·폐기 상태를 확정하고 변경 이력을 남긴다.

## 9. 확정 전 주의

- 수주와 발주, 출하와 배송, 매출과 수주금액, 입고와 검수, 공장과 사업장, 설비와 기계, 공정과 작업, 품목과 제품·자재는 이름이 유사해도 무조건 통합하지 않는다.
- 업무 모듈은 분류일 뿐 약어 중복을 허용하는 별도 네임스페이스가 아니다.
- SQLite도 독립된 데이터베이스 공급자로 취급하며 다른 DB와 같은 물리 명명 표준을 적용한다.
- 현재 자료에서 확인된 4개 SQLite 파일의 287개 컬럼 인벤토리와 별도 Commercial DDL은 서로 다른 근거로 관리한다. 두 자료의 범위를 합산해 실제 운영 DB 테이블 수라고 표현하지 않는다.


## 10. 확장 업무 용어 카탈로그 — 대표 개념과 관계 용어

### 10.1 등록 및 해석 원칙

이 절의 각 행은 **대표 개념 후보 1건**이다. 관계 용어는 해당 대표 개념을 찾기 위한 별칭이며, 관계 용어 자체를 별도 대표 용어 또는 약어로 등록하지 않는다. 약어 열을 일부러 두지 않았다. 대표 약어는 기존 전역 사전과의 충돌 검사를 완료한 뒤 별도 승인한다.

- 관계 용어 중 실제 업무 의미가 달라지는 단어는 별도 대표 개념 행으로 분리한다.
- 같은 한국어 단어가 여러 개념에 쓰이는 경우 관계 용어를 무조건 한 곳에만 귀속하지 않는다. 문맥·모듈·정의가 일치하는지 검토하고 모호성 레코드를 둔다.
- 거래 문서(주문·발주·입고·출고)와 그 문서의 행(Line), 이력(History), 상태(Status), 결과(Result)는 서로 다른 개념이다.
- 코드(Code), 코드그룹(Code Group), 코드값(Code Value), 코드체계(Code System)는 분리한다.
- 측정 정의(Measurement Definition), 측정 결과(Measurement Result), 시계열 측정값(Time-series Measurement)는 분리한다.
- 같은 개념이 여러 모듈에서 쓰이면 모듈 사용관계를 여러 개 연결한다. 대표 개념을 모듈 수만큼 복제하지 않는다.

## 11. 대표 용어·관계 용어의 저장 구조 권고

물리 약어 사전과 업무 관계 용어 사전은 논리적으로 분리한다. 관계 용어가 늘어나도 약어 발급 건수는 증가하지 않아야 한다.

### 11.1 대표 개념 테이블(논리 설계)

| 논리 속성 | 설명 | 제약 |
| --- | --- | --- |
| concept_id | 불변 개념 ID | PK, 변경 금지 |
| canonical_en | 대표 영문명 | 대표 개념 내 유일 |
| canonical_ko | 대표 한글명 | 검색·표시용 |
| canonical_abbr | 대표 약어 | 승인 후 전역 UNIQUE |
| concept_category | 개념 분류 | 필수 |
| definition | 정의 | 필수 |
| boundary_note | 포함·제외 경계 | 필수 |
| status | 표준화 상태 | 필수 |
| valid_from / valid_to | 적용 기간 | 버전·폐기 관리 |
| standard_version | 표준 버전 | 필수 |

### 11.2 관계 용어 테이블(논리 설계)

| 논리 속성 | 설명 | 제약 |
| --- | --- | --- |
| related_term_id | 관계 용어 ID | PK |
| concept_id | 연결할 대표 개념 ID | FK |
| term_text | 관계 용어 원문 | 정규화 검색키 별도 관리 |
| language_code | 언어 | 예: ko-KR, en |
| relation_type | 동의어·표기변형·업계표현·상위어·하위어·문맥유사어·혼동주의어 | 필수 |
| module_context | 특정 모듈에서만 유효한 문맥 | 선택 |
| usage_note | 사용 조건·예외 | 필수 |
| preferred_for_display | 대표 표시어 여부 | 대표어와 관계어 구분 |
| status | 승인·검토·폐기 | 필수 |

관계 용어의 검색키는 중복될 수 있다. 동일한 표현이 서로 다른 개념을 가리키는 동음이의어인 경우, 모듈 문맥과 정의를 함께 사용하여 판별한다. 관계 용어 문자열 자체에 전역 UNIQUE 제약을 두지 않는다.

### 11.3 개념-모듈 연결 테이블(논리 설계)

| 논리 속성 | 설명 |
| --- | --- |
| concept_id | 대표 개념 ID |
| module_code | 사용 모듈 |
| ownership_type | 소유·공유·참조 |
| module_definition | 해당 모듈에서의 추가 설명 |
| mapping_note | 타 모듈과의 연계·매핑 설명 |

한 개념이 ERP·MES·QMS 등 여러 모듈에서 사용되면 연결 행을 여러 건 둔다. 대표 개념과 약어는 한 건만 유지한다.

## 12. 약어 발급 전 검증 규칙

1. 먼저 개념 중복을 판정하고 대표 개념 ID를 확정한다.
2. 관계 용어를 대표 개념에 연결한다. 관계 용어에는 약어를 발급하지 않는다.
3. 기존 136개 사전 및 이 확장 카탈로그의 모든 대표 개념을 대상으로 후보 약어를 전역 검사한다.
4. 신규 대표 약어는 3자 소문자 영문을 우선한다.
5. 3자 충돌 시 의미를 유지하는 4자 후보를 검토한다.
6. 4자 충돌, 다의성, 발음·철자 혼동이 있으면 자동 확정하지 않고 보류한다.
7. 약어가 확정되지 않은 개념은 물리 컬럼명 생성 대상에서 제외한다.
8. 모듈별 약어 예외를 만들지 않는다.
9. 외부 표준 코드(예: ERP 공급자 필드, 산업 프로토콜 필드)는 외부 원문과 EDAN 대표 개념 매핑을 함께 보존한다. 외부 약어를 EDAN 내부 대표 약어로 무조건 채택하지 않는다.

## 13. 확장 사전 검토 상태

이 확장 카탈로그는 업무 범위와 대표 개념 후보, 관계 용어를 상세화한 설계 자료다. 모든 후보의 대표 약어가 확정되었다는 의미는 아니다. 기존 136개 용어와의 대표 개념 중복·동음이의어·약어 충돌 검토, 실제 테이블/컬럼 매핑, 업무 전문가 검토 후 표준 상태로 승격한다.

- 대표 개념 후보와 관계 용어는 문서에서 추적한다.
- 동의어 통합은 개념 의미가 일치할 때만 허용한다.
- 상위어·하위어·문맥 유사어·혼동 주의어는 별도 관계로 유지한다.
- 모든 약어는 전역 유일성 검증을 통과해야 한다.
- SQLite, Oracle, SQL Server, PostgreSQL은 같은 논리 사전과 약어를 공유한다.
